# 03 — 保留清理

**Spec:** `docs/specs/2026-08-16-mgdb-v1-pg-backup-design.md`

**What to build:** 让备份目录的磁盘占用有一个硬上限。每次备份**成功后**删除超出保留份数的最旧产物。

这是整个工具里唯一会销毁数据的代码，所以清理范围被严格限死：只有文件名符合本工具命名规则**且**前缀属于当前数据库的文件才进入候选集。备份目录很可能被设成下载目录这类混杂目录，这条约束保证别的文件绝对安全。

**Blocked by:** 02 — 原子写入 + 格式感知校验 + 格式可选

**Status:** 已完成

- [x] 备份成功后自动删除超出保留份数的最旧产物
- [x] 保留份数按数据库独立计数，可在全局默认值与单个数据源上分别配置，默认 14
- [x] 保留份数配置为 0 时不执行任何删除
- [x] 清理只影响文件名符合本工具命名规则、且**前缀属于当前数据库**的文件；目录中的其他文件与其他数据库的产物一律不动
- [x] 清理**绝不**扫描整个目录做模式匹配删除
- [x] 备份失败时不执行清理（不能出现既没有新备份、又丢了旧备份的情况）
- [x] ~~每个数据源有一个指向其最新产物的符号链接~~ **（已撤销，理由见下）**
- [x] 删除发生时打印被删文件的清单，删除动作可见而非静默
- [x] 计算待删列表的逻辑写成纯函数：输入候选文件列表与保留份数，输出待删列表
- [x] 本次刚落盘的产物永不进候选集（票面没有，实现中补的，理由见下）
- [x] 两个数据源的数据库名相同、又备份到同一目录时，配置层直接拒绝（同上）
- [x] 测试覆盖：往临时目录预置一批文件（含不合命名规则的杂文件、其他数据库的产物、符号链接），跑一次备份后断言哪些被删、哪些存活
- [x] 测试覆盖：不足保留份数、正好等于保留份数、保留份数为 0、备份失败四种情形下均不误删

**实现结果，两点偏离**：

1. **latest 符号链接整个撤销了。** 文件名已带秒级时间戳，排序即可看到最新的那份；
   固定指针不增加信息，却要在切换产物格式时二选一——留着旧格式的指针会指向一份
   实际更旧的备份，删掉又让人以为丢了东西。
2. **补了两条票面没有的约束**，都是为了防静默数据丢失：
   - 本次刚落盘的产物永不进清理候选集。目录里只要存在一份时间戳更晚的备份
     （时钟回拨、拷回旧目录、手工改名），新产物就会被判为最旧而删掉——
     工具打印「备份完成」、退出码 0，却在同一次运行里销毁了自己的产物。
   - 「0 表示永不清理」这条策略移出纯函数。混在一起时，「保留 1 份且要保护
     刚落盘的那份」算出的预算 0 会被误当成「永不清理」，该删的反而一个不删。
