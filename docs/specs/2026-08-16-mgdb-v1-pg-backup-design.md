# mgdb v1：PostgreSQL 备份命令行工具设计

## 问题陈述

我每天需要备份 manygames 的 PostgreSQL 数据库，目前靠 manygames 仓库里的一个脚本完成。这个脚本有几个让我不放心的地方：

1. **它只认一个数据源。** 连接串写死在环境变量里，想备份另一个库（比如本地库和线上库）就得改环境变量或者切 `NODE_ENV`，容易切错、备错。
2. **它会毁掉我上一份好备份。** 脚本让 `pg_dump` 直接写向目标文件，所以备份一开跑，上一份就已经被截断。如果这次跑到一半失败（网络断、磁盘满），我手里只剩一个残缺文件，而原来那份完好的已经没了。脚本里「文件大小是否为 0」的检查拦不住这种情况——残缺文件的大小远大于 0。
3. **旧备份无限堆积。** 不同日期的快照永远不删，磁盘占用没有上限。
4. **失败了我不一定知道。** 它把错误打到标准错误流，我在终端里手动跑时能看到，但这条路走不通任何「无人值守」的场景。
5. **每次都要记参数。** 备份目录、用哪个环境、输出到哪，都靠我自己记住并敲对。

更根本的问题是：我打算把备份变成日常习惯，最终挂成定时任务。而现在这个脚本既没有可选择的数据源，也没有失败通知，一旦挂到后台，它会安静地失败而我毫不知情——等到真需要还原的那天才发现最后一份可用备份停在三个月前。

## 解决方案

一个叫 `mgdb` 的命令行工具，装在本机全局可用。它有两种用法，共用同一套核心逻辑：

**不带参数敲 `mgdb`**，进入终端界面。第一眼看到的是状态面板：每个数据源的上次备份时间、成败、现有份数、占用空间，超过一定天数没成功备份的会标红。从这里可以进入备份流程（选数据源 → 确认输出目录和格式 → 执行），或者管理数据源（新增/编辑/删除）。

**带参数敲 `mgdb backup --source <名字>`**，不进任何界面，直接执行备份并以退出码表示成败。这条路径是为了将来能被定时任务调用而存在的，界面只是它的一层外壳。

数据源配置在本机一份配置文件里，新增时直接粘贴完整的 PostgreSQL 连接串（我手上现成的连接串就在各个项目的环境变量文件里，复制粘贴一步到位），工具解析出主机、端口、用户名、数据库名给我确认，也允许逐字段修改。

备份本身在三个地方比现在的脚本可靠：**先写临时文件、校验通过后才原子就位**，所以失败的一次绝不会毁掉上一份好备份；**校验是格式感知的**，不是简单看文件非空，中途截断的产物过不了；**成功后自动清理超出保留份数的旧备份**，磁盘占用有硬上限，而且清理只认本工具自己生成的、属于该数据库的文件。

失败时弹 macOS 系统通知主动推给我，同时把结果写进状态文件，界面下次打开就能看到「某个数据源已经 N 天没有成功备份了」。

## 实现决策

### 分层：核心层不依赖界面

工具分三层，依赖方向单向向下：

- **核心层** —— 配置读写、数据源连接串解析、备份编排、保留策略计算、状态记录、系统通知、备份工具定位。**零 React 依赖**，可以被单独引用和测试。
- **命令行层** —— 解析参数，合并优先级，调用核心层，把结果打印成文本，设置退出码。
- **界面层（Ink）** —— 状态面板、数据源管理、备份流程。**仅在无参数启动时被动态引入**，命令行路径完全不加载它。

这个约束来自「headless 为核心，界面只是外壳」这一决策。它的直接收益是：将来的定时任务路径不会因为加载界面运行时而变慢或变脆。

**不做数据库驱动抽象层。** 路线图上明确只有 PostgreSQL 的备份、还原和定时任务；其他数据库「可以考虑但暂时不做」。不同数据库的备份工具在参数、产物格式和还原语义上差异大到抽象层只能退化成「跑个子进程」，那不是抽象。将来真要支持时再抽，代价比现在预留一层假接口小。

### 核心入口：`runBackup`

命令行层和界面层调用的是同一个函数，签名形态为：

`runBackup(数据源名, 单次覆盖项, 依赖) → 备份结果`

**注入的依赖只有三个 port：**

| Port | 职责 | 为什么要注入 |
| --- | --- | --- |
| `runPgTool` | 执行 postgres 命令行工具 | 测试里替换成写出预置内容的假实现，避免测试依赖真实数据库。`pg_dump` 与校验用的 `pg_restore --list` **共用这一个 port**，所以子进程接缝始终只有一个 |
| `now` | 提供当前时间 | 让文件名里的时间戳可断言 |
| `notify` | 发送系统通知 | 断言失败路径确实通知了，且测试不会真的弹通知 |

**文件系统不注入，用真的**，测试时指向临时目录。原子重命名与删除语义正是要验证的行为，把文件系统换成假的等于在验证那个假实现。

### 备份流水线

1. 读配置，按 **命令行参数 > 数据源配置 > 全局默认值** 的优先级合并出本次的有效参数。
2. 定位备份工具：**配置了 `pgBinDir` 就以它为准，找不到即报错、不回退**；没配才走环境变量路径 → 常见安装位置探测。找不到时报出指明原因和解决办法的错误。
   （原设计是三级回退。改成「显式配置即权威」，是因为显式配置被环境里碰巧存在的另一个版本悄悄顶替时，「跑的不是我配的那个」这类问题最难排查。）
3. 确保输出目录存在。
4. 解析数据源连接串，拆出主机、端口、用户名、数据库名；**密码经环境变量传给子进程，不进命令行参数**（命令行参数在进程列表中对同机其他用户可见）。
5. 备份到输出目录下的临时文件。
6. **格式感知校验**：dump 格式要求文件头带 `PGDMP` 魔数、且内部目录能被完整列出；纯 SQL 格式要求文件尾部带有完整结束标记。任一不满足即判定为失败。
7. 校验通过后**原子重命名**到正式文件名。
8. **仅在成功后**执行保留清理，且**本次刚落盘的产物永不进候选集**。
9. 写状态记录。

**失败路径**（任一步失败）：删除临时文件，保持已有备份不变，写状态记录，发系统通知，以非零码退出。**中断（Ctrl-C）走同一套清理逻辑。**

### 产物命名

`<数据库名>-<年月日-时分秒>.<扩展名>`，扩展名 `sql` 或 `dump`。时间戳精确到秒，因此同一天多次备份不会相互覆盖——这与旧脚本「同日重跑即覆盖」的行为不同，是有意的改变：同日的第二次备份如果失败，不应该有任何机会污染当天早些时候那次成功的产物。

**前缀取数据库名，不取数据源名。** 数据源名是给人看的标签，随时会改；拿它当前缀意味着改一次名字，此前所有备份就从计数和清理里消失了。数据库名跟着连接串走，稳定得多。

代价是**两个数据源如果数据库名相同、又备份到同一个目录，产物会混在一起**：清理其中一个时会把另一个的备份当成「自己的旧备份」删掉。这是静默的数据丢失，因此**配置层直接拒绝这种组合**（数据库名相同但目录不同、或目录相同但数据库名不同，都放行）。

**不做「指向最新备份」的固定名字。** 文件名已带秒级时间戳，排序即可；固定指针不增加信息，却要在切换格式时二选一：留着旧格式的指针会指向一份实际更旧的备份，删掉又让人以为丢了东西。

### 保留策略

保留份数按**数据库独立计数**，默认 14，可在全局默认值和单个数据源上配置，设为 0 表示永不清理。

**清理逻辑写成纯函数**：输入「候选文件列表 + 保留份数」，输出「待删列表」。这是架构约束，不因为它不单独作为测试接缝而放松——它是整个工具里唯一会销毁数据的代码。「0 表示永不清理」这条**策略**不放在这个纯函数里，否则「保留 1 份且要保护刚落盘的那份」算出的预算 0 会被误当成「永不清理」，该删的旧备份反而一个不删。

**本次刚落盘的产物永不进候选集。** 只要目录里存在一份时间戳比现在更晚的备份（时钟回拨、从别处拷回旧目录、手工改名都会造成），排序后它排在最前，保留份数较小时刚生成的这份就会被判为「最旧」而删掉——工具打印「备份完成」、退出码 0，却在同一次运行里销毁了自己的产物。

**清理绝不扫描整个目录做模式匹配删除。** 只有同时满足「文件名符合本工具的命名规则」且「前缀属于当前数据库」的文件才进入候选集；符号链接与目录一律排除。这条约束的现实意义是：备份目录很可能被设成下载目录这类混杂目录。

### 配置

存放在用户配置目录下的 JSON 文件（不是代码仓库内），权限收紧到仅本人可读写。选 JSON 是因为零依赖且界面层写回简单。

**全局默认值**：输出目录、备份格式、保留份数、备份工具所在目录、「多少天未成功备份算超期」的阈值。

**每个数据源**：名字、连接串、以及可选的输出目录 / 格式 / 保留份数覆盖项（不填则继承全局默认值）。

**这三项覆盖的输入有三种意思，命令行与界面共用同一套规则**（写在一处，两边调用，避免规则漂移）：

| 输入 | 含义 |
| --- | --- |
| 没给这一项 | 保持不变 |
| 给了空串（界面留空、命令行 `--keep ""`） | **清除这项覆盖，回到全局默认** |
| 给了值 | 校验后写入 |

「清除」必须表达成显式的空值：配置合并是 `{...旧, ...新}`，光是省略掉的话旧值会被顶回来，清空就永远生效不了。另外，保留份数的空串必须在转数字之前挡住——`Number("")` 是 `0`，而 `0` 是合法取值（永不清理），不挡的话「清空」会静默变成「永不清理」。

**状态记录**是另一份文件，按数据源名存：上次运行时间、上次成功时间、本次成败、错误原因、产物路径与体积。它是状态面板和失败提醒的数据来源。

### 命令行接口

- 不带参数 → 进入界面，主屏是状态面板
- `backup` 子命令：指定数据源，可选覆盖输出目录、格式、保留份数
- `status` 子命令：打印状态，支持机器可读输出
- `source` 子命令组：列出 / 新增 / 编辑 / 删除数据源；`edit` 传空串即清除对应的覆盖项

界面里能做的每一个选择，都必须有等价的命令行参数。「清除某项覆盖」也在此列——它是界面表单的自然操作（把字段清空），所以命令行必须给得出等价写法。

### 备份子进程参数

沿用旧脚本的 `--no-owner --no-privileges`，保证产物不携带源库的属主和权限信息，将来能灌进不同角色的目标库。

### 格式嗅探（为 v2 预留，v1 不实现还原）

还原时判断文件格式必须**读文件本身的魔数**，不能读配置。理由：几个月前那份备份可能是用另一种格式生成的，而配置只反映当下。v1 不做还原，但产物命名和校验逻辑按这个前提设计，不引入「靠配置反推格式」的耦合。

### 安装与分发

独立仓库，通过 `bun link` 注册为全局命令，命令名 `mgdb`。改完代码立即生效、零构建步骤。v1 不做定时任务，开发反馈速度优先于自包含性。

### 对 manygames 仓库的改动

新工具**并行验证一段时间、确认可靠之后**（不是同一天），移除 manygames 中的旧备份脚本、对应的包脚本入口，以及环境变量示例文件中相关的备份目录说明。在此之前两条路径并存，作为切换期的保险。

## 测试决策

### 什么算好测试

只断言外部可观察的行为，不断言实现细节。对这个工具来说，「外部可观察」是指：**磁盘上最终出现和消失了哪些文件、状态文件里记了什么、通知有没有发、进程退出码是什么、以及备份子进程收到了哪些参数**。不断言内部函数被调用了几次，也不断言中间数据结构的形状。

这条标准的实际后果是：把「保留策略」的正确性表述成「跑完一次备份后，目录里还剩哪些文件」，而不是「计算函数返回了哪个数组」。

### 主测试接缝：`runBackup`

命令行层和界面层共用这一个入口，所以在这里测等于同时覆盖两条调用路径。

测试环境：真实临时目录 + 假的 postgres 命令行工具 port（`pg_dump` 与 `pg_restore` 共用一个 port，可被指使成功、失败、或写出截断产物）+ 固定时钟 + 假通知 port。

这一个接缝覆盖：

- 配置读取，以及参数优先级（命令行 > 数据源 > 全局默认值）的合并结果
- 连接串解析——通过断言假子进程收到的主机、端口、用户名、数据库名和密码环境变量来验证，包括 URL 编码密码的还原
- 文件命名与时间戳；前缀取数据库名，**改数据源名后历史备份仍被认作同一批**
- 临时文件的产生与就位
- 格式感知校验：合格产物通过、截断产物被拒
- 原子就位：**子进程失败或校验不通过时，上一份好备份必须原封不动**
- 保留清理：够份数不删、超份数删最旧、**名字不合规则的文件和别的数据库的文件必须活着**、失败时不清理、**刚落盘的产物永不被本次清理删掉**
- 同库同目录的配置被拒
- 状态文件的写入内容；失败时保留此前的成功时间
- 失败路径：通知已发、退出码非零、状态写不进去时也要上报
- 中断时的临时文件清理

其中「往临时目录预置一批文件，跑一次备份，断言哪些被删、哪些活着」这一个测试，就能覆盖清理逻辑的大部分边界。

### 实际用到的其他接缝（原设计只打算开一个）

原设计写的是「整个 v1 只有 `runBackup` 一个接缝」。实现下来是 5 个。每多开一个都在对应测试文件顶部写了理由，这里汇总：

| 接缝 | 为什么另开 |
| --- | --- |
| `runBackup` | 主接缝，见上 |
| `collectStatus` | 独立的读路径。它算「超期」和「占用空间」，这两件事 `runBackup` 永远不会执行到 |
| `main()`（命令行入口） | `source` 系列命令没有值得抽出的编排函数，在入口测比在下面的配置函数上测更高，顺带盖住参数解析与退出码 |
| 界面渲染（`StatusPanel` / `App`） | 「该不该标红」是界面里唯一的真判断，也是「以为在备份其实早就挂了」的唯一预警，值得钉死 |
| `parseOverrides` | 命令行与界面共用的校验规则，在共享处测一遍，胜过在两个调用点各测一遍 |

**明确不单独开接缝的**：文件名生成、格式魔数嗅探、配置文件读写。它们在上述接缝里被间接覆盖，单独开只会增加接缝数量而不增加覆盖。

**仍然没有自动化覆盖的**：界面的按键交互与表单流转（选择、切屏、逐字段编辑）。只有手动验证。

**明确不测的**：真实的备份子进程执行。这是一条子进程调用命令，手工跑一次就验证了；把真实数据库拉进测试会让测试变慢、变脆，也违背项目「测试中不使用真实基础设施」的既有约定。

### 与既有约定的关系

项目既有的测试约定禁止在测试中使用真实基础设施。用假的备份子进程 port 而不是拉起真实数据库，正是这条约定在本工具上的落地方式。测试运行器沿用 `bun test`，与 manygames 各包一致。

### 一处需要报备的偏差

在拷问阶段确定的方向是「只测纯逻辑」。上述方案比那个范围**更宽**——它是一个跑在真实临时文件系统上的编排测试。守住的部分是「不跑真实备份子进程」；放开的部分是「不限于纯函数」。理由是这个工具的真实风险在接线而非算法：写错目录、删错文件、失败后没回滚，全都是纯函数单测照不到的地方。

## 范围之外

- **还原功能。** 留到 v2。这意味着 v1 期间产出的备份**其可还原性是未经证实的**——见「补充说明」。
- **定时任务。** 留到 v3。v1 只保证 headless 入口存在且行为正确，不生成任何系统级定时任务配置。
- **异地备份 / 上传对象存储 / 推送到远程主机。** 工具只写本地目录，异地副本由使用者自行解决。
- **PostgreSQL 以外的数据库。** 不做驱动抽象层。
- **数据库内容浏览。**
- **备份历史浏览界面。** 状态面板只做汇总（上次时间、份数、占用），不做逐份列表和逐份操作。
- **多数据源并行备份。** 一次一个。
- **备份文件加密。**
- **增量备份 / 预写日志归档。** 只做全量逻辑备份。
- **macOS 以外的平台。** 系统通知依赖 macOS 原生能力。
- **备份前的数据库版本兼容性预检。** 见「补充说明」中的已知风险。

## 补充说明

### 已知并被接受的风险

1. **备份只存在本机。** Mac 丢失或硬盘损坏时，备份与原件一同消失。这是明确的决定，异地副本由使用者自行解决，工具不涉及上传。

2. **v1 没有还原，等于备份未经验证。** manygames 的 schema 有 21 个自定义枚举类型。纯 SQL 产物往非空库灌回时必然遇到类型已存在的冲突，到底该用「先清理再建」还是「必须灌进空库」，要等 v2 真正实现还原时才会有答案。**在 v2 落地之前，累积的这些备份文件的可用性属于未经证实状态。** v1 的格式感知校验只能证明产物结构完整，不能证明它灌得回去。

3. **线上数据库版本未知。** 本机备份工具为 17.6。若线上服务端版本高于 17，备份工具会直接拒绝执行。这会在第一次备份线上库时暴露。v1 不做预检，只保证错误信息清晰可读。

### 将来会踩的坑（记录在此，v3 处理）

本机的备份工具安装在 Homebrew 的库路径下，**这个路径不在 macOS 定时任务服务的默认环境变量里**。v3 挂定时任务时第一次运行必然报「找不到可执行文件」。v1 已经通过「可配置备份工具所在目录」为此留好了出口，但真正的验证要等 v3。

### 与既有文档的关系

- **术语。** 「数据源」「备份」「保留份数」在 manygames 的领域术语表中不存在——这是一个新领域，不与现有词汇冲突，也不需要替换任何既有术语。
- **架构决策记录。** manygames 现有的 4 条 ADR 全部属于租赁与会员领域，与本工具无交集，无冲突需要报备。
- **本工具是独立仓库**，不进 manygames 的 monorepo。理由：它是个人工具而非产品的组成部分，放进 monorepo 会让它白白进入产品的构建与测试流水线，而它的生命周期与产品无关。

## 与最初设计的偏离

本文已同步到实现现状（2026-08-16，v1 的 8 张票全部完成）。正文各处已按实现改写，这里汇总材料性的偏离，便于对照最初的设计意图：

| 项 | 最初设计 | 现状 | 为什么 |
| --- | --- | --- | --- |
| 产物前缀 | 数据源名 | **数据库名** | 数据源名是可随时改的标签，拿它当前缀意味着改一次名字，此前所有备份就从计数和清理里消失。配套加了「同库同目录」的配置层拦截 |
| 格式命名 | `custom` | **`dump`** | `custom` 是 pg_dump 自己的说法，脱离上下文没有意义；`dump` 与产物扩展名一致。传给 pg_dump 的参数取值仍是 `--format custom`，那是它的 CLI 契约 |
| 「最新备份」指针 | `<名>-latest.<扩展名>` 符号链接 | **不做** | 文件名已带秒级时间戳，排序即可；指针在切换格式时会产生歧义 |
| 备份工具定位 | 配置 → PATH → 常见位置，三级回退 | **配置了就是权威，不回退** | 显式配置被环境里碰巧存在的另一版本悄悄顶替时最难排查 |
| 测试接缝数量 | 只开 `runBackup` 一个 | **5 个** | 见「实际用到的其他接缝」一节，每个都有单独理由 |
| 清理的保护范围 | 未提及 | **刚落盘的产物永不进候选集** | 目录里存在「未来时间戳」的文件时，新产物会被判为最旧而删掉 |
| 覆盖项的清除 | 未提及 | **空值即清除，回到全局默认** | 原先设上就去不掉 |

**尚未做的**：Ticket 09（移除 manygames 仓库里的旧备份脚本）。它的第一条验收条件要求新工具并行运行不少于两周且累计成功不少于 10 次，时间未到。
